# Hashly v0.1 — WYSIWYG Markdown Reader

**Status:** Partially shipped (2026-04-29 — slice #18 only; remaining slices deferred to a follow-up milestone PR)
**Author:** deanchanter
**Date:** 2026-04-28

## Summary

Hashly v0.1 is a native Mac app that opens a single `.md` file and renders it as a "pretty," WYSIWYG-readable document — with a toggle to a WYSIWYG-edit mode for occasional changes. It exists because non-engineers being handed AI-generated SDD docs today either fight VS Code's IDE shape, stare at raw `#`/`**` syntax, or pay for iA Writer / Typora. v0.1 is reading-first, not editor-first.

## Problem & motivation

VS Code is confusing for a PM opening their first AI-generated SDD spec — sidebar, command palette, and a preview extension they have to install — and even once they get there, the raw markdown isn't "pretty." Paid tools (iA Writer, Typora) solve this but cost money, which non-eng SDD participants don't want to pay for a doc someone else handed them. Today they cope by squinting at raw markdown in whatever editor they have, or bouncing back to Slack. This matters now because SDD has made markdown a primary artifact landing in front of non-engineers, not a side artifact for developers.

## Users & primary use case

**Primary persona:** A PM reading their first SDD document — a spec.md created by an AI system or handed to them by someone else. Frequency: occasional at first, expected to grow as SDD adoption grows in their org.

**Use case walkthrough:**

The PM receives an SDD spec.md (generated by an AI agent, or passed to them by an engineer). They open it in Hashly — primarily to *read it top to bottom* and understand what's being proposed. They may need to make light edits inline (a clarification, a correction). They save and hand it back. The reading view is the surface they spend almost all their time in; editing is the secondary mode.

## Scope

### In scope — acceptance criteria

- [ ] Open any `.md` file via Finder double-click **or** File > Open menu and see it rendered in the reading view in <1s with no setup.
- [ ] All standard CommonMark elements (headings, lists, code blocks, tables, links, images, blockquotes) render correctly.
- [ ] A toggle switches between rendered reading view and a WYSIWYG-edit view; default on open is the reading view.
- [ ] A dirty indicator is visible whenever there are unsaved edits.
- [ ] Light and dark modes are both supported.

### Out of scope

The following are deferred to the v0.1 backlog (good ideas, not v0.1):

- Multi-file or folder browsing
- Tabs
- Find and replace
- Image paste
- Export to PDF / HTML
- Drag-drop file open (including drop onto Dock)
- Recent-files list
- Settings / preferences UI
- Spellcheck

### Constraints

- **Platform:** Mac only.
- **Native app** (not Electron — Tauri is acceptable as it uses the system WebView).
- **Works offline** — no network dependency.
- **Single `.md` file** at a time.
- **Light and dark modes** both required (inherited hard constraint from vision).

## User experience

### Flow

1. **Entry:** User double-clicks a `.md` file in Finder, or opens Hashly and uses File > Open. (Drag-onto-Dock not supported in v0.1.)
2. **Land:** App opens directly into the rendered reading view of that file.
3. **Read:** User reads top-to-bottom, scrolls, follows links, etc.
4. **(Optional) Edit:** User toggles to WYSIWYG-edit view, makes a change. Dirty indicator appears.
5. **Save:** User saves (Cmd+S). Dirty indicator clears.
6. **Close:** User closes window.

### Edge cases & failure states

- **Binary / non-UTF-8 file with `.md` extension:** Show a friendly "can't open this file" message. Don't crash. **Must handle.**
- **Unsaved edits on close:** Standard "Save / Don't Save / Cancel" dialog. **Must handle.**
- **Malformed markdown:** Render best-effort. Never crash. **Must handle.**
- **Huge files (10MB+):** Deferred. v0.1 targets typical spec docs (<1MB). Document as a known limitation.
- **File deleted / moved on disk while open:** Deferred. Keep the in-memory copy editable; save will recreate or fail loudly.

## Technical design

### Surface area

- **Stack:** Tauri (Rust core + system WebView).
- **WYSIWYG editor library:** Milkdown (chosen specifically to mitigate the "build a WYSIWYG editor from scratch" risk).
- **Distribution:** GitHub release with a `.dmg`.
- No backend, no network calls, no telemetry.

### Data model

_N/A — no new persistence. The `.md` file on disk is the only state. Window size/position, last theme, follow-OS-theme, and any user preferences are explicitly not persisted in v0.1._

### Decisions & open questions

**Decisions made:**

- Tauri over pure-Rust GUI (egui / iced / Slint) — pure-Rust would mean building WYSIWYG markdown rendering ourselves, which is a serious undertaking. Tauri lets us reuse a mature JS WYSIWYG lib.
- Milkdown over Tiptap / ProseMirror direct — picked as the concrete bet; revisit if it doesn't pan out.
- Reading view is the default surface, edit view is the toggle — driven by the persona being a *reader* of AI-generated docs first.
- Vitest as the frontend test runner — Rust integration tests + manual host smoke aren't enough to lock down Milkdown wiring (read-only mode, fixture rendering, edit toggle, dirty/save round-trip). See [task #13 / issue #18](https://github.com/deanchanter/Hashly/issues/18). Tests are colocated with `src/`; downstream slices (#3, #6, #7) ship with TS-level coverage rather than leaning on manual checks alone.

**Open questions:**

- Mac signing / notarization details (Gatekeeper friction is a known risk; not yet planned out).
- Whether theme follows OS by default or has an in-app toggle (no settings UI in v0.1, so probably follows OS — but unconfirmed).

## Risks & mitigations

- **WYSIWYG editing is genuinely hard; a half-working WYSIWYG could feel worse than VS Code.** — Use Milkdown rather than build the editor from scratch.
- **Tauri learning curve.** — Manage as it comes; no specific mitigation locked in.
- **Scope creep.** — The Out-of-scope list above is the firewall; treat backlog items as v0.2+ even when tempting.
- **Motivation loss (solo build).** — Manage as it comes.
- **Mac signing / notarization friction.** — Manage as it comes; flagged as open question.

## Alternatives considered

- **Tell the PM to use a free Chrome extension markdown viewer** — Chrome extensions are not hardened; not a credible recommendation for an SDD-default tool.
- **Fork MarkText (existing free WYSIWYG, low momentum)** — Old codebase; better to start fresh.
- **Do nothing; keep writing tutorials around VS Code's built-in preview** — Already been tried; the VS-Code-shaped experience is exactly the problem.
